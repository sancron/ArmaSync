- Ziele: WebDAV-Upload über `OPTIONS`, `PROPFIND`, `MKCOL`, `PUT`, `DELETE`. Zugangsdaten nur über HTTPS und nur an die Herkunft der Basis-Adresse; Weiterleitungen werden nie vom Client selbst gefolgt und auf andere Herkunft abgelehnt. HTTP ohne Zugangsdaten bleibt zulässig.
- Nicht im Scope: Verdrahtung in Sync, CLI, GUI (MIG-042); Auflistung und XML-Auswertung; Sperren; Fortsetzen; Schlüsselauthentifizierung; Proxy; echte Server.
- Ergebnis: **Umgesetzt.** `OPTIONS`, `PROPFIND`, `MKCOL`, `PUT`, `DELETE` über den blockierenden `reqwest`-Client (Option b aus ADR-0010). Der erste Zwischenstand auf `ureq` ist durch die Methodenbeschränkung von `ureq` 3.4.2 überholt. 17 Loopback-Tests unter Windows bestanden (HTTP und TLS).
- Abnahmekriterien und geplante Checks: siehe [Bericht](../changes/2026-10-25-MIG-040B.md); Ausführung unter Windows: `cargo fmt --check`, Clippy `-D warnings`, `cargo test --workspace --locked`, `cargo +1.85.0 test --workspace --exclude armasync-gui --locked`, Markdown-Linkprüfung, `git diff --check`.
- Blocker und offene Punkte: Interoperabilität mit echten WebDAV-Servern; zwei TLS-Stacks im Programm (`ring`, `aws-lc-rs`) als Folgeentscheidung; ob ein CMake-Programm für den Build nötig ist, nicht abschließend geprüft.
