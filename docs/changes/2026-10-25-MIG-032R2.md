# 2026-10-25 — MIG-032R2 — Härtung der Teildateien gegen Hardlinks und Namensaustausch

- Zeitpunkt: 2026-10-25, Europe/Berlin. Claude (Eigentümer und Integrator). Basis `development` @ `c0b5eef`; Branch `claude/mig-032r2-partial-hardening`; [Task](../tasks/MIG-032R2.md); Ergänzung zu [ADR-0009](../adr/0009-resume-range.md), Abschnitt „Härtung“.
- Auslöser: Review-Befund zu MIG-032R (P1, zwei Punkte): Hardlink als `.part` kann beim Fortsetzen außerhalb des Zielordners kürzen; `.state` wurde per `fs::write` über einen Link geschrieben; Namen konnten zwischen Prüfung und Öffnen getauscht werden.

## Was geändert wurde

* `crates/armasync-adapters/src/localfs/partial.rs` (neu geschrieben, Verhalten nach außen unverändert):
  * Vorhandene Namen werden nie zum Schreiben geöffnet. Frischer Start: Eintrag entfernen, `create_new`.
  * Fortsetzen: gültige Bytes lesend aus dem alten Namen in eine neue Datei `<name>.tmp` kopieren, Quellhandle vor dem Rename schließen, dann Rename. Der Kopierpfad ist eine bewusste Kostenentscheidung gegenüber dem Schutz.
  * Zustand: Schreiben über `…state.tmp` (neu angelegt) und Rename.
  * Öffnen mit Linkschutz: Windows `FILE_FLAG_OPEN_REPARSE_POINT` und Freigabe ohne `FILE_SHARE_DELETE`; Linux/Android `O_NOFOLLOW`; macOS/iOS `O_NOFOLLOW`. Prüfung auf dem Handle (`is_plain_handle`), nicht auf dem Namen.
  * Ein Ablehnungsgrund bei der Fortsetzung führt zum frischen Start (kein Fehler für den Aufrufer).
* `crates/armasync-adapters/tests/localfs_partial_sentinel.rs` (neu, 3 Fälle): externer Sentinel, verlinkt an `.part` (Fortsetzungspfad), an `.state` (Schreibpfad) und an `.part` im frischen Pfad. Der Test prüft, dass der Sentinel unverändert bleibt. Verlinkt wird per Hardlink; ein Symlink ist nur Fallback, wurde nicht benötigt. Keiner der Fälle wurde übersprungen.
* ADR-0009 um einen Abschnitt „Härtung“ ergänzt.

## Warum der Kopierpfad

Stabiles Rust (MSRV 1.85) kann die Linkzahl unter Windows nicht lesen (`number_of_links` ist nur über `windows_by_handle` nightly verfügbar). `unsafe` ist im Workspace verboten, eine Win32-Abfrage über `windows-sys` scheidet deshalb aus. Statt eine Linkzählung zu prüfen, wird der alte Name nie beschrieben. Die gültigen Bytes werden kopiert; die Gesamtprüfung über Größe und Hash bleibt unverändert.

## Zweite Runde: Namensaustausch während des Übergangs

Ein Review (2026-10-25) fand: Das Resume-Handle wurde geschlossen, bevor der Name per Pfad umbenannt und erneut schreibend geöffnet wurde. Dazwischen konnte ein Angreifer mit Schreibrecht den Namen durch einen Hardlink ersetzen. Dasselbe Muster galt beim Commit.

**Änderungen:**

* Schreiben nur noch über den Handle, den der Adapter per `create_new` angelegt hat. Nach dem Kopieren des Präfixes wird **derselbe** Handle bis zum Ende des Laufs benutzt; `open_existing_write` entfällt. Unter Windows hat der Handle `FILE_SHARE_DELETE`, damit das Umbenennen möglich bleibt.
* `PartialFile::commit_to(target, expected)`: Nach dem Rename wird der Zielinhalt über einen Handle mit Linkschutz gelesen und gegen den erwarteten Hash geprüft. Stimmt er nicht, wird der Name entfernt und `Integrity` gemeldet. Der In-Memory-Adapter prüft ebenso.
* Test-Seam `LocalDirectory::set_rename_hook` (versteckt): wird vor jedem Rename per Name aufgerufen.
* Zwei deterministische Race-Tests (`a_name_swapped_during_the_commit_…`, `a_name_swapped_during_a_resume_…`): Der Name wird genau im Übergang gegen einen Hardlink auf eine externe Sentinel-Datei getauscht. Die Sentinel-Datei bleibt unverändert, es wird keine unverifizierte Datei installiert.
* Mutationsprüfung: Mit abgeschaltetem Nachprüfschritt schlagen beide Race-Tests fehl; mit dem Schritt bestehen sie.

**Prüfungen (Windows, lokal):** `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --locked --no-fail-fast` (inkl. GUI und Ende-zu-Ende) und `cargo +1.85.0 test --workspace --exclude armasync-gui --locked` bestanden.

**Grenzen (ausdrücklich):**

* Ein Angreifer mit Schreibrecht kann das Ziel ersetzen; dann ist das Ergebnis ein Integritätsfehler. Die alte Zieldatei ist in diesem Fall verloren.
* Unix-Pfadrennen (RB-01) bleibt offen; die Nachprüfung deckt den Commit ab, aber ein Namensaustausch zwischen Nachprüfung und späterem Zugriff bleibt theoretisch möglich.
* Die Gesamtdatei wird beim Commit einmal zusätzlich gelesen (Kosten).

## Dritte Runde: Löschfehler nach fehlgeschlagener Nachprüfung

Review zu `0745350`: Scheiterte das Entfernen der unverifizierten Zieldatei nach dem Rename, ignorierte der Code den Fehler und meldete trotzdem „entfernt“.

* `commit_to` prüft das Ergebnis des Entfernens. Gelingt es: `Integrity` („removed“). Scheitert es: `FileSystem` mit dem Hinweis, dass die unverifizierte Datei am Ziel liegen bleiben kann.
* `PartialFile::commit_to` im Core beschreibt jetzt die tatsächlichen Ausgänge, einschließlich des Verlusts des alten Zielinhalts nach einem Prüffehler nach dem Rename.
* **Nicht getestet:** Der Löschfehler-Pfad hat keinen deterministischen Test. Ein offener Handle auf die Zieldatei würde den vorausgehenden Rename selbst blockieren (Windows). Das bleibt offen.
