# 2026-10-19 — MIG-030D — CLI `sync plan` / `sync run` und Ende-zu-Ende-Prüfung

- Zeitpunkt: 2026-10-19, Europe/Berlin. Claude. Basis `39de92676b745002502c3a8cc9dd83f1848c860b`; Branch `claude/mig-030d-sync-cli`; [Task](../tasks/MIG-030D.md).
- Umgesetzt: `armasync sync plan <repository-id> --destination <dir>` und `armasync sync run …` (`--dry-run`, `--delete-extra`, `--managed-root <folder>`…, `--config`, globale `--json`/`--quiet`). Die CLI ist nur Composition Root: Repository-URL aus der Bibliothek → `HttpRepository` (liest die Metadaten **einmal** als `HttpSnapshot`) → `application::plan`/`apply` → `LocalDirectory`. Keine Sync-Logik in der CLI.
  * `PlanOptions::protected_paths` kommt **immer** aus `SyncMetadata::plan_options` (versteckte Ordner und nicht unterstützte, komprimiert geführte Dateien).
  * Löschen nur mit `--delete-extra` **und** mindestens einem `--managed-root` (sonst Exitcode 2, bevor irgendein Netzwerkzugriff stattfindet); `--managed-root` ohne `--delete-extra` und unsichere Ordner (`..`) werden abgelehnt.
  * `plan` und `run --dry-run` öffnen das Ziel schreibgeschützt (es wird nicht einmal die Sperrdatei angelegt); `run` nimmt die exklusive Zielsperre (MIG-030H); das Zielverzeichnis wird nie implizit angelegt (fehlend = Exitcode 5).
  * Ausgabe: Text mit Plan, Warnungen (komprimierte Dateien, unsichere Namen, geschützte Extras), Ergebnis und Hinweis, wenn das Repository als „braucht Zugangsdaten“ markiert ist (Authentifizierung ist nicht implementiert, es werden **nie** Zugangsdaten gesendet); `--json`-Envelope `sync-plan`/`sync-run` mit Zusammenfassung, Schritten (ohne `keep`), Warnungen mit stabilen Codes, `unsupported_paths`, `protected_paths`, Bericht; Fortschritt höchstens einmal pro Sekunde auf stderr (nicht bei `--json`/`--quiet`). Exitcodes: 0, 2 (Aufruf/unbekannte ID/`--delete-extra` ohne Ordner), 3 (zweiter Lauf auf demselben Ziel), 4 (Netzwerk/TLS/HTTP-Status), 5 (Dateisystem), 6 (Integrität: falscher Hash/Größe), 7 (Metadaten), 8 (nicht unterstütztes Schema).
- Ende-zu-Ende-Tests (Windows 11, echte Binärdatei, echter HTTP-Adapter, echtes Dateisystem, lokaler Loopback-Server mit den MIG-001-`small`-Metadaten und aus dem dokumentierten Generator neu erzeugten Nutzdaten; Repository über den echten `import`-Befehl angelegt; keine öffentlichen Server, keine Nutzerdaten): 14 Tests –
  * Plan ohne Änderung; erfolgreicher Lauf mit bytegleichen Dateien (SHA-1 gegen das Manifest geprüft), JSON-Envelope, zweiter Lauf lädt nichts erneut; die komprimierte Datei wird nie angefordert; keine `Authorization`-/`Cookie`-Header; `--quiet`; `--dry-run`;
  * Ersetzen veralteter Dateien; Extras bleiben standardmäßig; Löschen nur mit Flag + Ordner; geschützter Ordner und lokal entpackte Kopie einer komprimierten Datei überleben, Warnungen `extra-kept-protected`;
  * `--delete-extra` ohne Ordner und unsichere Ordner: Exitcode 2 vor jedem Netzwerkzugriff; unbekannte/ungültige ID: 2; fehlendes Ziel: 5, nichts wird angelegt;
  * **verfälschter Download** (gleiche Länge, anderer Inhalt): Exitcode 6, alte Zieldatei unverändert, keine Temporärdatei; bei leerem Ziel wird nichts installiert;
  * HTTP 404/500/401 und **abgebrochene Verbindung** (zu kurzer Körper): Exitcode 4, vorhandene Datei unverändert, keine Reste; nicht erreichbarer Server: 4;
  * **ungültiges TLS-Zertifikat** (selbstsignierter Loopback-Server): Exitcode 4 „secure connection failed“, **keine** Anfrage gesendet, nichts geschrieben;
  * **zweiter Lauf** auf demselben Ziel: Exitcode 3 „another ArmaSync run“; der erste Lauf (Server hält nach 1000 Bytes an) wird mitten in der Übertragung **hart beendet**: die alte Zieldatei ist unverändert, die Staging-Datei bleibt als Rest zurück, der nächste Lauf gegen einen gesunden Server findet die Sperre frei, räumt den Rest auf und installiert beide Dateien korrekt.
- Gesamt: fmt, clippy `-D warnings`, **288 Tests bestanden** (vorher 274), MSRV 1.85 ohne GUI-Crate bestanden, CLI-Baum GUI-frei (keine neue Produktionsabhängigkeit; Dev: `rcgen`, `rustls`). Ein transienter, nicht identifizierter MSRV-Fehlschlag in einem Lauf unter Last war in neun Wiederholungen nicht reproduzierbar; wahrscheinliche Ursache war die zeitabhängige Kontrollphase des Angreifertests (nach der Änderung wartet er bis zu 30 s auf den ersten Tausch).
- **Abbruch:** Ein Ctrl+C-Handler ist **nicht** implementiert (Exitcode 130 bleibt reserviert). Wird der Prozess beendet, bleibt die Zieldatei unverändert (Staging + atomarer Austausch, oben belegt); ein Rest wird beim nächsten Lauf aufgeräumt, die Sperre endet mit dem Prozess. Kooperativer Abbruch im Use-Case ist auf Bibliotheksebene getestet (MIG-030P/C).
- **Offen/zurückgestellt:** WSL/Linux lokal; GitHub-CI pausiert; **Unix-Race der Pfadgrenze (Release-Blocker für „race-freie Pfadgrenze unter Linux“, [LOCAL_FS_THREATS](../migration/LOCAL_FS_THREATS.md))**; echte Server, Unternehmens-TLS-Inspektion, expliziter Proxy, Authentifizierung, Resume, ZIP-Blätter, Ctrl+C-Handler, Zeitgrenzen bei sehr großen Repositories ungemessen.
- **Einordnung:** Ein Plan-/Run-Ablauf mit echter Binärdatei, HTTP-Adapter und Dateisystem ist gegen einen lokalen Loopback-Server unter Windows belegt. Das ist **keine** Aussage über reale Server oder Linux; die Plattformvalidierung (WSL/Linux, Abschluss) und echte Altserver fehlen, ebenso die GUI-Anbindung (MIG-031).
