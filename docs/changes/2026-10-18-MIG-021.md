# MIG-021 — Offline-Export und neutraler Import lokaler Altdaten

- Datum: 2026-10-18 (Europe/Berlin). Eigentümer und Integrator: Claude.
- Branch `claude/mig-021-import`; Basis `development` @ `734a20b` (Reservierung `3983e02`); Code-Commits `ba0e161`, Importer; CLI-Commit (`feat(MIG-021): add armasync import command`), `6351a80` Exporter, Golden-Dateien, Tests, CI-Schritt, Dokumente; [Taskdatei](../tasks/MIG-021.md).
- Warum: P2 braucht einen kontrollierten Weg von Altdaten in das neue Speicherformat (COMPATIBILITY, „Lokaler Migrationsweg“), mit Vorschau, Backup, Abbruch, Wiederholbarkeit und ohne Geheimnisse.

## Was

- **Format** `armasync.import` Schema 1 ([IMPORT_SCHEMA](../migration/IMPORT_SCHEMA.md)): Repositories (ohne Zugangsdaten), Profile (geordnete Repositoryverweise), Herkunft, Hinweise. Kein Feld für Geheimnisse; jedes Dokument mit secret-ähnlichem Feldnamen wird abgelehnt.
- **Importer** (`armasync-adapters::import`): `Importer::preview` (nur lesend) und `apply` (erneute Planung gegen den aktuellen Bestand, Abbruchprüfung, Vorab-Sicherung `library.pre-import-<zeit>.json.bak`, ein atomarer Commit über den `LibraryStore`, Journal ohne Namen/Adressen/Geheimnisse). Deterministische IDs und Konfliktrichtlinien `keep-both` (Standard), `fail`, `replace`; Wiederholung ändert nichts; nachträglich ergänzte Repositories lösen Profilverweise auf.
- **CLI** `armasync import <datei> [--apply] [--on-conflict …] [--config <dir>] [--json]`; Vorschau ist Standard; Exitcodes 0/2/3/5/7; `--json`-Envelope auch für Fehler; kein Warten auf Eingaben. Neue Abhängigkeit des CLI-Crates auf `armasync-core` (Workspace-intern).
- **Offline-Exporter** `migration-tools/legacy-export/export.py` (Python, nur Standardbibliothek, nutzt den Leser aus MIG-001 per Import): exportiert Profile aus unverschlüsselten Altdateien, listet verschlüsselte Repositorydateien als übersprungen, exportiert nie Kennwörter, Logins, Favoritenserver oder Schlüssel, überschreibt nichts, schreibt nicht ins Altverzeichnis, lehnt Streams mit abweichender Klassenversion ab (Tabelle für `Profile`, `TreeDirectory`, `TreeLeaf`).
- **Fixtures/Golden:** `fixtures/neutral-import/from-legacy-local.json` (Ausgabe des Exporters für die MIG-001-Fixtures), `synthetic-full.json` (von Hand, `.invalid`-Domains).
- CI: zusätzlicher Schritt „Offline exporter tests“ im Job `fixtures`; CLI_CONTRACT und CI.md ergänzt.
- Keine neuen Cargo-Abhängigkeiten (sha2, serde, serde_json bereits vorhanden); MSRV bleibt 1.85; kein Keyring, keine persistente Credential-Speicherung.

- Linux (WSL2 Ubuntu, Rust 1.99.1, Python 3.12, LF-Clone, Nicht-root): fmt, clippy, 141 Tests, GUI-freier Baum, Exporter-Tests 9 (Ausgabe identisch zur Golden-Datei), Verifier 0 Probleme.
- Getestet: Vorschau schreibt nichts (auch kein Verzeichnis); Anwenden, Wiederholung (Datei, Journal, Backup unverändert), Backup byte-gleich; Abbruch vor dem Commit lässt Bibliothek/Journal/Dateiliste unverändert; Fehler beim Commit (blockiertes Backupziel) lässt Bibliothek unverändert, entfernt temporäre Dateien, kein Journaleintrag; beschädigte Bibliothek wird nie überschrieben; defektes Journal wird gemeldet; `fail`/`keep-both`/`replace`; Auflösung nachgereichter Repositories; 20 feindliche/ungültige Importdokumente (Geheimnisfelder, Zugangsdaten und Query in URLs, `file://`, unbekannte Felder, Duplikate, Steuerzeichen, neuere/fehlende Version, überlange Texte, Tiefe 100 000 Ebenen, > 4 MiB, fehlende Datei) ohne Echo der Werte; CLI-Exitcodes und JSON; Exporter: Eingabe per SHA-256 unverändert, keine Fixture-Geheimnisse/Adressen im Export, Ausgabe nicht überschrieben, Ausgabe im Altverzeichnis abgelehnt, 15 ungültige Fixtures plus leere/zufällige Dateien führen zu Hinweisen statt Absturz, falscher Objekttyp, deterministische Ausgabe.
- Beim Test gefunden und behoben: (1) Der Leser akzeptierte die Fixture mit geänderter `serialVersionUID` als gültiges Profil; der Exporter prüft jetzt die Klassenversion. (2) `os.path.commonpath` warf bei Pfaden auf verschiedenen Laufwerken eine Ausnahme. (3) Der Exporter hätte nach einem Fehler beim Öffnen eine fremde Ausgabedatei löschen können; er entfernt nur Dateien, die er selbst angelegt hat. (4) Beim ersten Anlauf war das neue Modul nicht in `lib.rs` eingebunden und wurde daher nicht kompiliert; erst die Importtests deckten das auf.

## Nicht geprüft / offen

- **Verschlüsselte `.a3s.repository`-Dateien werden nicht importiert**; Entscheidung offen (ADR-0003: Schlüsselkonstante in Rust oder einmaliger JVM-Export; Rechte-/Herkunftsfrage RQ-01). Der Export aus einem echten Altverzeichnis liefert daher heute Profile **ohne** Repository-Definitionen. Weitere Quelle: MIG-022 (Autoconfig der Server).
- Profilinhalte (Startoptionen, Addons), Einstellungen, Favoritenserver nicht übernommen (MIG-050/053).
- Keine realen Nutzerdateien (bewusst), keine großen Altverzeichnisse; Exporterlimits sind Fixture-Werte. Keine Gegenprüfung mit einer echten Altanwendung.
- Windows-Dateisperren, echter Prozessabbruch mitten im Commit, gleichzeitige Importe nicht getestet; Strg+C der CLI nicht verdrahtet; keine GUI-Anbindung (MIG-031).
- Keine Rechtefreigabe; RQ-01..RQ-08 unverändert offen. Die Altfeld-/Klassennamen im Exporter sind Wire-Daten nach ADR-0003.
